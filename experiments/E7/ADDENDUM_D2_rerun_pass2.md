# Addendum D2：bl6 第二遍重跑（c1 因 inode 耗尽作废 → c2）

日期：2026-11-14。性质：**协议修订**（新增批次 ID 和一个容量门禁）。代码包、场景表、预测、执行器、评分器、判定规则都不变。
用户批准（聊天，2026-11-14）：“我们一边整理一边重跑第二次实验可以吗？第一次正式实验是有结果的”。

## D2.1 事实

- 资格验证 `ecr-bl6q-srv-b1`：10/10，r1 审计 PASS（Erratum D1），有效。
- 第一遍 `ecr-bl6x-srv-b1`（boot 1 `3059c176…`）：2848/2848，重放 CONSISTENT，G-K 0 命中，有效。
- 第二遍 `ecr-bl6x-srv-c1`（boot 2 `6ef06c75…`）：在第 2621/2848 个 attempt 处，客机根文件系统的 inode 用光（`df -i` 只剩 28 个，字节空间还有 6.3G），出现 `OSError: [Errno 28]`，重放、导出和内核日志抓取都失败。服务器 agent 按协议停下：没有重试、没有删除。
- 原因是环境容量不足：bl6 每遍的单元数是 bl5 的 1.9 倍，而 runbook 只检查了字节空间，没有检查 inode。这与方法、代码和数据无关。

## D2.2 为什么不在原盘上接着跑

runner 的 attempt-index 是跨批次共用的（`run_bl6c.py` 的 `attempts_of` / `claim_attempt`）。原盘的 `async-sim-bl6c/attempt-index` 里已经有 c1 的第 1 次尝试。在原盘上换新 ID 跑的话，每个单元都会被记成第 2 次尝试（`---a2`，带 `retry_of`），不满足 G-D 要求的“有效首次尝试”，还需要另写 continuation 授权。所以必须换一块干净磁盘。

## D2.3 修订内容

1. **c1 作废**。`ecr-bl6x-srv-c1` 不再使用。它的证据（私有批次、attempt-index、public 目录、日志）全部保留，作为作废记录交回。原客机磁盘保持原样，不删除，不修改，也不再启动。
2. **新磁盘**：从原始 VMDK（SHA `07360d6431e637e7cf51e5e5879cf83b20dfa9d419b7a3fa7bbc02c1b0a03e9d`）重新克隆一块磁盘，首次启动前扩容，再在客机里扩展根文件系统。UUID 和 MAC 不变。
3. **新批次 ID**：资格验证 `ecr-bl6q-srv-b2`，第二遍 `ecr-bl6x-srv-c2`。两者在新磁盘的同一次启动中运行（记为 boot 3），先资格验证，再跑第二遍。这和 boot 1 的安排相同（资格验证后跑第一遍）。boot 3 与 boot 1 必然不同，所以满足“两遍分别在两次冷启动中运行”。
4. **资格验证照原样重做**：10 个单元，仍用 `audit_qualification_bl6_r1.py`（Erratum D1）审计，加上负对照、两种重放、定稿和 G-K。全部 PASS 后才能写 c2 的授权文件（模板见 `guest_tools/qualification-authorization-c2.TEMPLATE.json`）。
5. **身份要求**：新磁盘上生成的 `execution-manifest-bl6.json`，SHA 必须与 b1 用过的那份**完全相同**（`6f27a54e…`，以服务器记录的完整值为准）。生成工具是确定性的，输入也相同，不一致就停。
6. **新增门禁 G-S（存储容量）**：在资格验证之后、c2 开跑之前，对客机根文件系统检查：
   - 空闲 inode ≥ **1,300,000**；
   - 空闲字节 ≥ **20 GiB**。
   - 依据：c1 失败时已用 1,212,388 个 inode，包含系统本身、资格验证、完整一遍和 0.92 遍，所以一遍最多约 1,212,388 / 1.92 ≈ 631,000 个。1,300,000 约为两倍余量。不扩容的同尺寸新盘满足不了这个门槛，所以必须扩容。
   - 不通过就停下来报告，不许删除文件来腾空间。
7. **G-D 的两遍**改为：run1 = `ecr-bl6x-srv-b1`，run2 = `ecr-bl6x-srv-c2`。判定规则不变（2848 个唯一单元、都是有效首次尝试、11 个评分字段和发送标签一致、执行清单身份一致）。
8. **G-K**：boot 3 的内核日志要覆盖 `ecr-bl6q-srv-b2` 和 `ecr-bl6x-srv-c2` 两个批次。规则不变。

## D2.4 预先写下的分析规则

- **主结果仍取第一遍 b1**，与 Addendum D 相同。第二遍只用于 G-D 可复现性检查，不作独立样本。所以 c2 的结果不会改变任何报告数字，重跑没有“挑结果”的空间。
- **c2 运行期间可以先复核 b1**，算 H1–H3。这些结果在 G-D 通过后才冻结。代码、场景和预测都已冻结，看到 b1 的结果不会影响 c2。
- **c1 的 2621 个单元**只做描述性比对：逐字段对照 b1 的同名单元，结果写进补充材料。这个比对不能代替 G-D，也不改变本补遗的任何决定，无论比对结果如何，c2 都照常运行。
- **c2 如果又停下**（任何原因）：停下，保留证据，不开 c3。是否再跑由用户决定。这种情况下论文只能报告 b1，并写明 G-D 没有完成；c1 的部分比对作为补充。
- 论文的 Threats 一节要写明：c1 因 inode 耗尽作废、换盘重跑、新批次 ID，以及本补遗。
