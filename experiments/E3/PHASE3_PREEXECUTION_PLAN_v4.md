## 1. D8：规划器调用记录的代码身份绑定（v4 的改动）

### 1.1 改了什么

v3 → v4 共修改 7 个文件，没有新增文件。补丁 `phase3_code_v3_to_v4.diff` 包含 7 个文件、29 个 hunk。

| 文件 | 改动 |
|---|---|
| `tools/planner_recorder.py` | 代码身份与输入身份**分开**记录：<br>• **代码身份**是明确给定的代码清单文件（`ECR_CODE_MANIFEST`）的 SHA-256，必须等于 `ECR_CODE_IDENTITY`；<br>• 每次调用前，对这次调用实际执行的文件重新计算哈希：桥接文件；T 路径还包括臂的两个 `.ts` 文件。这些文件必须列在清单中，且哈希一致；<br>• J 路径：strip 清单必须与 `ECR_JS_IDENTITY` 一致、状态为 COMPLETED、由同一个 Node 生成；实际存在的 `.js` 和 `package.json` 必须与 strip 清单一致；strip 清单记录的 TS 输入哈希必须等于代码清单中 `arms/<arm>/*.ts` 的哈希；<br>• Node：每次调用都核对二进制文件的大小和修改时间（完整哈希由调用方在运行前后核对）；<br>• 输入身份：每次调用的 stdin 哈希，另外可以选填输入集身份 `ECR_INPUT_IDENTITY`，它**不会**被当作代码身份；<br>• 实际执行的文件及其哈希写入 `executed_files`；<br>• 身份不符时，照样写入记录，但**不启动 Node**，退出码为 7 |
| `tools/planner_records.py` | 任一调用的身份检查不是 OK，或者记录中**没有**身份字段（v4 之前的格式），都判为 INCOMPLETE；同一次尝试中如果出现多个（代码、JS）身份，也判为 INCOMPLETE |
| `tools/replay.py` | 回放前，对记录中的 `executed_files` 逐个重新计算哈希（路径可以映射），不一致时判为 CODE_IDENTITY_MISMATCH，**不重新运行**；同运行时模式下，如果 Node 哈希与记录不同，判为 RUNTIME_IDENTITY_MISMATCH，也不运行；这两种判定都会使状态变为 STOP。v4 之前的记录照常回放，但标为 `UNVERIFIABLE_RECORD_PREDATES_BINDING`，**不回填** |
| `tools/qualify_planner.py` | 新增必填参数 `--code-manifest`。运行前核对：包内每个文件都与清单一致；strip 清单与代码清单、实际的 JS 文件都一致；Node 的完整哈希正确。任何一项不一致都以退出码 3 退出，不调用规划器。运行结束后再核对一次 Node 的完整哈希。summary 中新增 `identity` 一节（代码、JS、输入、Node），且代码身份与输入身份不同 |
| `tools/make_execution_manifest.py` | 新增必填参数 `--candidate-manifest`。包内文件必须与候选清单完全一致（除了在 VM 上生成的 `arms_js/`），并记录 `candidate_manifest_sha256` |
| `runner/run_r2.py` | 把执行清单只读部署到公共目录，作为记录器核对用的代码清单；把身份相关的环境变量传给记录器；在守卫核对完 Node 哈希之后，记录 Node 的大小和修改时间 |
| `tests/test_phase3_tools.py` | 假桥接的测试夹具也带上代码清单和 strip 清单；新增 6 个身份测试（见 §2） |

身份绑定形成以下一条链，每一环都有核对：

候选清单 v4 → 执行清单（生成时核对，并记录候选清单的哈希）→ 部署文件（runner 守卫核对）→ 每次调用实际执行的文件（记录器核对）→ 回放时实际执行的文件（回放工具核对）。

### 1.2 不回填历史记录

- 第 1 次资格验证（v2 代码）的记录，"代码身份"一栏写的是输入文件的哈希，**原样保留，不修改**。

- 这些记录**不能**作为 v4 尝试的有效记录：`planner_records.check` 会因为缺少身份字段而判为 INCOMPLETE。

## 4. D9：固定的证据收集方案（只确定方案，需要单独批准）

- **触发条件**：
  - 集合 A：Q1/Q4 中原始调用失败的记录（非零退出、超时、信号、输出格式不对）；
  - 集合 B：Q3 同运行时回放中，判定不是 IDENTICAL_BYTES 的记录；
  - 集合 C：Q3 跨运行时回放中，判定既不是 IDENTICAL_BYTES、也不是 EQUAL_EXCEPT_RUNTIME_VERSION 的记录（在主机上处理）；
  - 身份不符的记录不在这三个集合中：遇到它们时直接停止，不做诊断。
- **回放集合**：
  - 在 VM 上处理 A ∪ B，在主机上处理 C；
  - 按记录路径排序，每个集合最多取前 20 条，其余的列为"未诊断"；
  - 把选中的记录文件（每条 5 个文件）**复制**到新的诊断目录，原记录不动。
- **次数**：每条选中的记录用同一模式、同一个 Node 回放**恰好 3 次**，超时 30 秒；每次回放都写入新的 `--evidence-dir`。每个集合最多 60 次执行。
- **停止条件**：
  - 出现工具故障（身份不符、记录缺失、回放工具出错）时，立即停止诊断；
  - 否则把 3 × 选中条数全部执行完，之后不再增加任何回放；
  - **不自动重试**。
- **结果**：
  - 单独标为 DIAGNOSTIC，报告每条记录在 3 次中复现失败的次数；
  - **不改变**原来的 Q1/Q3/Q4 判定，也不改变资格结论。
- **实现方式**：使用现有的 `replay.py` 加文件复制，不需要改代码。
