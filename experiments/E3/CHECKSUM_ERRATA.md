# P3-A 证据目录校验清单勘误（2026-10-16）

**对象**：`outputs/20261016/ECR_P3A_正式运行_ecr-p3a-20261016-r1/`（下称证据目录）。

**原则**：证据目录中的任何文件都没有改动，包括旧清单 `SHA256SUMS.txt`。更正清单和本勘误都放在证据目录之外，即本目录。

## 1. 错误

旧清单 `SHA256SUMS.txt` 的情况：

| 项 | 值 |
|---|---|
| 真实 SHA-256 | `4c67025a615ccb9bda9dd7746237cdcd6ae1baaba26c97ded27866ec389b2e3e` |
| 行数 | 30 |
| 文件修改时间 | 2026-10-16 12:07:34 UTC（文件系统时间，没有第三方证明） |

存在两个问题：

1. **第 1 行列出了清单自己**，记录的哈希是 `e3b0c442…b855`，即**空文件的 SHA-256**。这一行无论如何都无法通过核对。
2. **两份正式报告是在清单之后写入的，所以没有列入**：
   - `P3A_FORMAL_RESULTS_REPORT.md`，12:13:59 UTC；
   - `P3A_FORMAL_RESULTS_REPORT_r1.md`，12:21:35 UTC。

之前的交付说明曾写"目录内 30 个文件的哈希"，这个数字把清单自身的那一行也算进去了。实际有效核对的文件是 29 个。

## 2. 成因（推测，未经复现）

本会话的记录显示，旧清单是在证据目录内用下面这条命令生成的：

```
find . -type f | sort | xargs sha256sum > SHA256SUMS.txt
```

按照 shell 的一般行为，`>` 重定向会在 `find` 运行之前先创建一个空的 `SHA256SUMS.txt`，于是 `find` 把这个空文件也列了进去，记录下的就是空文件的哈希。这与观察到的现象一致，**是最可能的成因，但我没有复现，不把它当作已证实的事实**。

## 3. 更正

由脚本 `scripts/ecr_p3a_checksum_correction.py`（`22049fe0…`）生成。脚本只读取证据目录，输出写到本目录。

| 文件 | 内容 |
|---|---|
| `SHA256SUMS_r1.txt`（`885420b7…`） | 证据目录中的全部 **32** 个文件：29 个旧清单已列的文件、旧清单本身（用它的真实哈希 `4c67025a…`）、两份报告。新清单在证据目录之外，所以不会包含自己 |
| `correction_record.json` | 生成时间（UTC 2026-10-16 13:19:55）、逐项比较结果、脚本哈希 |
| `independent_check_sha256sum.txt` | 独立复核的原始输出 |

### 与旧清单逐项比较的结果

| 项 | 结果 |
|---|---|
| 旧清单中除自身外的条目 | 29 个，与当前文件**全部一致**；没有不一致，也没有缺失 |
| 旧清单的自身条目 | 记录值为空文件哈希，实际值是 `4c67025a…`，此行作废 |
| 旧清单没有列入的文件 | 2 个，即上面两份报告 |

### 独立复核

用 coreutils 的 `sha256sum -c` 在证据目录内核对 `SHA256SUMS_r1.txt`。这与生成清单的 Python `hashlib` 是两种不同的实现。

- 结果：**32/32 OK**，退出码 0。
- 复核前后，旧清单的哈希仍是 `4c67025a…`，修改时间仍是 12:07:34 UTC，确认没有被改动。
- 正式报告 r1 的哈希是 `feed60ce…`，与先前记录相同。
